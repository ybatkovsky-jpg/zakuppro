# Спецификация требований к ПО (SRS): Mini-MRP «ПРОМЕБЕЛЬ»

## 1. Архитектурная концепция и Стек технологий

**Архитектура:** **Модульный монолит (Modular Monolith)**.
*Обоснование:* Микросервисы на данном этапе — это избыточная сложность (проблемы с распределенными транзакциями, DevOps-накладные расходы). Монолит обеспечивает консистентность данных (критично для склада и финансов), а модульная структура позволит в будущем легко вырезать отдельные контуры (например, AI-агента) в микросервисы, если нагрузка возрастет.

**Стек технологий:**
*   **Backend (Основной API):** Python (FastAPI). *Обоснование:* Идеален для интеграций, работы с AI, парсинга Excel. FastAPI дает высокую скорость и строгую типизацию (Pydantic), что важно для финансов. Существующие MVP, судя по репозиториям, также на Python, что упростит миграцию.
*   **Frontend (UI):** React (Next.js) + TypeScript + Ant Design (или MUI). *Обоснование:* Next.js обеспечит быстрый рендеринг сложных таблиц (спецификации, BOM). Ant Design имеет отличные готовые компоненты для Kanban-досок, таблиц и форм.
*   **AI-Agent / Bot layer:** Python (LangChain / LangGraph), Telegram Bot API, OpenAI API (GPT-4o). *Обоснование:* LangGraph позволяет строить конечные автоматы (State Machines) для агента, где он не отправит письмо, пока не сверит счет — это критично для безопасности.
*   **База данных:** PostgreSQL. *Обоснование:* Реляционная БД обязательна для транзакционности (финансы, резервирование на складе). JSONB-поля помогут хранить сырые ответы от LLM или банков.
*   **Message Broker:** RabbitMQ + Celery. *Обоснование:* Надежные очереди для асинхронных задач (отправка email, ожидание ответа от LLM, загрузка банковских выписок). Если процесс упадет на середине, он перезапустится.

## 2. Высокоуровневая архитектура (High-Level Architecture)

Система состоит из 5 контуров:

1.  **Web App (Frontend + API):** Интерфейс для менеджеров. Канбан-доски проектов, таблицы спецификаций, ручная сверка счетов, склад.
2.  **Telegram Bot Gateway:** Принимает Excel-файлы от владельца, авторизует его (по chat_id), отправляет счета на оплату, пушит алерты.
3.  **AI-Agent Worker (Celery):** Слушает очередь. Парсит Excel, формирует промпты для LLM, вызывает API OpenAI, принимает решения, сохраняет результаты в БД.
4.  **Email Worker (IMAP/SMTP):**
    *   *Outbound:* Отправляет сформированные агентом запросы поставщикам (с копией на рабочую почту).
    *   *Inbound:* Раз в N минут опрашивает почтовый ящик (IMAP). Если пришло письмо с вложением (счет) — загружает его в БД и передает задачу AI-Agent на сверку.
5.  **Bank Worker (Cron):** Раз в сутки забирает выписку (по API банка, 1С-клиент-банку или через парсинг email от банка) и мапит платежи.

## 3. Data Model (Основные сущности БД)

*   **Project** (id, name, client, status [Канбан: Проектирование, Закупки, В производстве, Монтаж], total_cost).
*   **ProjectItem (BOM)** (id, project_id, name, sku, qty, supplier_id [nullable], stock_item_id [nullable], status [К закупке, Запрошено, Счет получен, Оплачено, На складе, В производстве]).
*   **Supplier** (id, name, email, requisites).
*   **PurchaseOrder** (id, project_id, supplier_id, status [Сформирован, Отправлен, Счет сверен, Частичная поставка, Закрыт]).
*   **Invoice** (id, purchase_order_id, file_url, raw_text, status [Ожидает сверки, Ошибки, Сверен, Ожидает оплаты, Оплачен]).
*   **Payment** (id, invoice_id, amount, bank_transaction_id, payment_date).
*   **UnresolvedTransaction** (id, amount, description, bank_date, status [Не распределено, Привязано вручную]).
*   **StockItem** (id, name, sku, qty_total, qty_reserved, qty_available).
*   **ProductionTask** (id, project_id, status [Ожидание комплектации, В работе, Готов к отгрузке, У заказчика]).

## 4. Функциональные требования (Модули)

### Модуль AI-Агента
*   **Use Case 1: Загрузка BOM.** Пользователь кидает Excel в ТГ. Агент с помощью Pandas и LLM распознает структуру (какая колонка — артикул, какая — поставщик), очищает от мусора, создает `Project` и наполняет `ProjectItem`.
*   **Use Case 2: Сверка счетов.** Из Email Worker приходит PDF/Excel счет. LLM извлекает табличную часть. Система сравнивает с `PurchaseOrder` (Fuzzy Matching — нечеткий поиск для опечаток типа "Петля блабла" вместо "Петля бла"). При 100% совпадении — статус "Сверен". При несовпадении — формирует текст письма-уточнения.
*   **Use Case 3: Напоминания.** По крону проверяет `PurchaseOrder` со статусом "Частичная поставка" или давностью > X дней, инициирует отправку email-напоминания.

### Модуль Закупок и Коммуникаций
*   **Use Case 1: Группировка запросов.** Система группирует `ProjectItem` по `supplier_id`. Для позиций без поставщика система ищет возможных поставщиков по категории товара (из справочника) и создает несколько запросов.
*   **Use Case 2: Email-робот.** Формирует письмо по шаблону: "Добрый день, прошу выставить счет... Реквизиты: ...". Отправляет через SMTP. В копию (BCC) ставит рабочую почту компании.
*   **Use Case 3: Частичные поставки.** Если поставщик пишет "Позиций А нет, будет завтра, счет на Б", менеджер в UI может разбить заказ, перевести часть в производство, а для А поставить статус "Ожидание" и настроить триггер напоминания.

### Модуль Управления Проектами
*   **Kanban-доска:** Драг-энд-дроп статусов проекта. Переход из "Закупки" в "Производство" **блокируется**, если есть хоть одна `ProjectItem` со статусом ниже "На складе" (если не стоит галка "Игнорировать нехватку" от владельца).
*   **Ручное управление:** Возможность добавить `ProjectItem` в уже созданный проект (расходники, крепеж) с автоматическим пересчетом себестоимости.

### Модуль Производства и Комплектации
*   **Use Case 1: Матрица готовности.** Экран "Комплектация проекта" — таблица с цветовой индикацией (Зеленый — всё есть, Желтый — часть оплачено/в пути, Красный — не заказано/нет на складе).
*   **Use Case 2: Запуск в работу.** Смена статуса `ProductionTask` на "В работе" возможна только при 100% комплектации.

### Модуль Склада
*   **Use Case 1: Резервирование.** При создании BOM система ищет `StockItem` по артикулу. Если `qty_available > 0`, она списывает его из `qty_available` в `qty_reserved` и ставит `ProjectItem` статус "Со склада" (без создания заказа поставщику).
*   **Use Case 2: Списание.** При выдаче со склада в производство/монтаж `qty_reserved` обнуляется, `qty_total` уменьшается.
*   **Use Case 3: Пополнение.** Оприходование позиций от поставщика увеличивает `qty_total` и `qty_available` (сначала гасит резерв под проекты, остаток уходит в свободный).

### Модуль Финансов
*   **Use Case 1: Загрузка выписки.** Парсинг 1С / CSV. Мапинг по ИНН поставщика и Сумме.
*   **Use Case 2: Автоматическое связывание.** Если Сумма + ИНН = Сумма счета + ИНН поставщика -> `Invoice` = Оплачен, создается `Payment`.
*   **Use Case 3: Ручная сортировка.** Если мапинг не удался (например, ИНН не совпал, или оплачено больше/меньше), транзакция падает в таблицу `UnresolvedTransaction`. Бухгалтер/Владелец в UI в два клика привязывает её к нужному счету или создает расход.

## 5. Интеграционные потоки (Integration Flows)

### Flow 1: Загрузка спецификации (BOM) и создание проекта
1.  Владелец кидает Excel в Telegram.
2.  Bot Gateway валидирует пользователя, сохраняет файл (S3/Local), кладет задачу в RabbitMQ (`process_bom`).
3.  AI Worker берет задачу, Pandas парсит Excel в сырые строки.
4.  LLM чистит данные (убирает пустые строки, нормализует названия).
5.  Backend создает `Project` (Статус: Закупки) и пачку `ProjectItem`.
6.  Backend проверяет склад: если позиция есть, ставит статус "Резерв со склада".
7.  Backend группирует оставшиеся позиции по `supplier_id`. Для позиций без поставщика — создает "Виртуальные заказы" на подбор.
8.  AI Worker генерирует тексты писем, Email Worker их отправляет.
9.  В Telegram владельцу летит ответ: "Проект Мебель-Х создан. 45 позиций. Отправлено 5 запросов поставщикам. 12 позиций зарезервировано со склада".

### Flow 2: Проверка комплектации перед запуском в производство
1.  Менеджер в UI нажимает кнопку "Перевести в производство" у проекта.
2.  Backend делает запрос: `SELECT * FROM ProjectItem WHERE project_id=X AND status NOT IN ('Delivered', 'ReservedFromStock')`.
3.  Если список не пуст — UI показывает модалку: "Невозможно запустить. Не хватает: [Список]".
4.  Если список пуст — статус меняется, создается `ProductionTask`.

### Flow 3: Загрузка банковской выписки и оплата
1.  Bank Worker по API скачивает выписку за вчера.
2.  Для каждой расходной операции ищет `Invoice` со статусом "Ожидает оплаты" и совпадающим ИНН/Суммой.
3.  Если найдено: `Payment` создается, `Invoice` = Оплачен, Владельцу в ТГ пуш: "Оплачен счет от Поставщика А по проекту Б".
4.  Если не найдено: создается `UnresolvedTransaction`.

## 6. Требования к AI/LLM

*   **Парсинг Excel:** Сначала использовать `pandas` для конвертации в CSV/JSON. LLM вызывать только для "грязных" таблиц (объединенные ячейки, многоэтажные шапки). Модель: **GPT-4o** (отлично работает со структурированным текстом и дешевая).
*   **Сверка счетов (Fuzzy Matching):** Поставщики часто меняют "Шуруп 4x16" на "Шуруп потай 4х16". Использовать **Embeddings** (векторизацию) или алгоритм **Levenshtein distance** (расстояние Левенштейна) в связке с LLM. Промпт LLM: *"Сравни список А (Заказ) и список B (Счет). Найди расхождения в количестве, артикулах, пропущенные позиции. Верни JSON формата..."*
*   **Простановка поставщиков:** Для позиций без поставщика LLM анализирует категорию товара (напр. "профиль алюминиевый") и ищет в БД поставщиков с тегом "Профиль", формирует им запрос. Если поставщиков нет — пишет владельцу в ТГ: "Не знаю, у кого купить [Товар]".

## 7. План миграции и рефакторинга (на основе текущих MVP)

1.  **Анализ легаси:** Провести аудит `erp-mvp` и `zakuppro`. Скорее всего, модели БД (SQLAlchemy/Django ORM) можно переиспользовать.
2.  **Унификация БД:** Создать единую миграцию (Alembic) на основе лучшей схемы из двух MVP, добавить недостающие таблицы (`UnresolvedTransaction`, `StockItem`).
3.  **Рефакторинг API:** Переписать эндпоинты на FastAPI (если MVP были на Django/Flask), объединив бизнес-логику.
4.  **Переиспользование UI:** Вычистить React-компоненты из MVP, собрать их на базе Ant Design Pro (там есть готовые шаблоны для ERP).
5.  **Разработка нового:** Написать с нуля Worker-ы (Email, AI) и Telegram Bot, так как этого функционала ранее не было.
6.  **Стратегия запуска:** Импортировать данные из Google Таблиц в новую БД скриптом. Запустить систему параллельно с таблицами на 2 недели для сверки.

## 8. Non-Functional Requirements

*   **Безопасность:**
    *   Авторизация в Telegram строго по `chat_id` владельца.
    *   Доступ к API банка и почты через переменные окружения (Vault / `.env`), токены только с правами чтения (для банка).
    *   Ролевая модель в Web UI (Владелец — видит всё; Менеджер — только свои проекты; Склад — только остатки).
*   **Надежность (Fail-safes - КРИТИЧНО):**
    *   **Human-in-the-loop:** AI-агент **никогда** не отправляет письма или деньги напрямую без подтверждения. Все отправки писем со счета сначала падают в UI (или ТГ) в статус "Черновик", владелец жмет "Подтвердить отправку".
    *   **DLQ (Dead Letter Queue):** Если LLM вернула невалидный JSON или парсинг счета упал, задача не теряется, а попадает в очередь ошибок, откуда её можно перезапустить или обработать руками.
    *   **Транзакции БД:** Списание со склада и резервирование должны быть в одной транзакции (ACID), чтобы не возникло ситуации "списали, но не зарезервировали".
*   **Логирование:** Все действия LLM (промпты, ответы, токены) пишутся в таблицу `LlmLogs` для аудита и улучшения промптов.
